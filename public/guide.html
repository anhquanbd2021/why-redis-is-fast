Why Redis is fast — the mechanics

"In-memory" is the slogan. Three mechanisms are the machinery — each removes a different cost, each has its own edge.

1. RAM vs. disk — nanoseconds vs. milliseconds

A main-memory read costs ~100 nanoseconds. An SSD read costs ~100 microseconds (~1,000×); a spinning disk can cost ~10 milliseconds (~100,000×). Databases hide this with buffer pools and caches of their own, but a miss still reaches disk. Redis keeps the working set in RAM — a GET is a pointer dereference, not a disk seek. The latency lab replays this: 20 reads through the DB pay the latency 20 times; through the cache, once.

2. One thread, no locks

Redis runs commands on a single event-driven thread over non-blocking I/O. No locks, no mutex queues, no context switches — and every command is atomic for free, which is why counters and rate limiters are trivially correct on it. The edge: one slow command stalls everyone. KEYS * on a big keyspace, or an O(n) read over millions of members, blocks every client. Production habit: SCAN/HSCAN/SSCAN/ZSCAN cursors instead of full scans.

3. The data structure is the performance

Strings, hashes, lists, sets, sorted sets — the type matched to the access pattern is where the speed comes from. The type lab proves it with a leaderboard: fetch-all-and-sort touches every row per read, while a sorted set costs ZINCRBY (log n) per update and ZREVRANGE 0 9 for the top ten — a fixed, tiny cost at any table size. The anti-pattern to unlearn: JSON blob per key, deserialize to read one field.

4. Cache-aside, and the stampede

The default placement: app checks Redis → miss → read DB → populate with a TTL → return. One slow read, then fast hits. The failure arrives when a hot key expires: every concurrent request misses at once and all of them query the database. The lab makes it visible — run naive, watch the DB-query count and the peak-concurrency counter; run single-flight and the same cold wave produces exactly one DB fetch. Other fixes: a short lock on the fill, jittered TTLs, or proactively refreshing keys before expiry.

5. Honest limits

  • Memory is the ceiling — the dataset must fit in RAM; eviction policies (allkeys-lru etc.) choose what drops when you hit it.
  • A cache is disposable — the database stays the source of truth. Persistence options (RDB snapshots, AOF log) exist but make Redis a different role: a deployment decision, not an accident.
  • Single-threaded cuts both ways — it buys atomicity and predictability; it also means one heavyweight command pauses the world.
